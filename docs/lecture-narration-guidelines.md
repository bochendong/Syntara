# 课程笔记讲解稿标准

本文档记录课程笔记重写讲解稿时的质量标准。目标不是给每页 slide 配一段旁白，而是让播放过程像老师在课堂上带学生一步一步看图、理解、判断、计算和迁移。

## 核心原则

讲解稿要回答四个问题：

- 学生现在应该看哪里？
- 为什么现在要看这里？
- 这一页如何承接上一页，并把问题推给下一页？
- 看完这一页后，学生应该带走什么判断方法？

不要把讲解稿写成 slide 的复述。slide 上已经有的文字不用完整念一遍，讲解稿要补上页面没有直接写出来的内容：入口问题、因果关系、计算动机、常见误区、检查方法和下一页过渡。

## 工作方式

一次只处理一本 notebook。

先看完整本 notebook 的 contact sheet 或逐页图片，确认课程主线和页面类型。不要一次批量改很多本，因为讲解节奏、难点密度和学生掉队位置会不一样。

处理顺序建议：

1. 读取 notebook 当前 scene、actions、spotlight 结构。
2. 先建立整本 notebook 的 `courseSpine`：本节主问题、主线、最终回扣。
3. 为每页建立 `pageMove`：上一页解决了什么、这一页推进什么、下一页为什么自然出现。
4. 看每页 slide 图片和 hotspot，判断页面承担的教学功能与真实可讲区域。
5. 保留已有 spotlight 目标，围绕这些目标扩写 speech。
6. 每页写成慢节奏讲解，而不是快速提示。
7. 写入数据库后验证每页都有 speech，且 spotlight 的 `elementId` 都存在。

## 整课主线与上下页衔接

不要把每页当成独立旁白。一本 notebook 应先有整课主线，再写每页讲解。

推荐先写这四类规划文本：

- `courseSpine.logline`：整节课用一句话到底在训练什么能力。
- `courseSpine.centralQuestion`：学生从第一页带到最后一页的主问题。
- `pageMove.fromPrevious`：这一页从上一页的哪个结论或困惑接过来。
- `pageMove.toNext`：这一页结尾把问题自然交给下一页。

每页讲解至少要出现三种连接：

- 开头承接上一页：例如“上一页我们发现检查例子不够，所以这一页需要一条正式规则。”
- 中段回到主题：例如“这一步回到本节主线：用有限工作覆盖无限多个命题。”
- 结尾推向下一页：例如“下一页把这个模板放进整除命题，看归纳假设怎样变成整数方程。”

如果一页讲完后可以任意换到别的页，说明它还没有真正嵌入课程主线。

## 每页讲解结构

常规页面建议按这个节奏写：

1. 进入页面：说明这一页接上一页在解决什么问题。
2. 视线定位：告诉学生先看哪个区域。
3. 观察对象：先描述图、公式或题目中具体出现了什么。
4. 解释原因：说明为什么这一步成立，或者为什么要这么选。
5. 学生停顿：关键处给一句“先停一下想一想”或“请注意这里”。
6. 方法收束：把本页变成一句可迁移的判断方法。
7. 下一页过渡：自然说明下一页要解决的新问题。

不要每页只有 3-4 句。对数学课件，概念页、定义页、例题页通常需要 8-16 段 speech，复杂例题可以更长。

## Action 与 Speech

`spotlight` 应该先于对应讲解出现。不要先说“看这里”，然后画面还没有聚焦。

一个 spotlight 可以配多段 speech。推荐做法是：

- 第一段：带学生观察这个区域。
- 第二段：解释这个区域为什么重要。
- 第三段：给出判断、计算或错误提醒。

如果某页只有一个大图或封面，也要有开场讲解，不能让第一页没有 speech。

## Spotlight 聚焦框标准

长讲解稿不能只复用原来少量的大区域 spotlight。讲解变慢以后，视觉引导也要同步变细，否则学生会听到很多判断点，却不知道具体该盯住哪一块。

原则：

- 每个讲解段落进入新的视觉单元前，应该先切换到对应 spotlight。
- 不要为了追求数量而每句都换框。一个框可以覆盖同一视觉单元内连续几段 speech。
- 例题页要尽量按“题目、选法、计算、答案、提醒”分别聚焦。
- 三列或多卡片页面不能只框整片区域，要给每个例题、每个性质卡或每个公式行单独热点。
- 封面页如果没有语义 hotspot，也要补透明热点框，至少覆盖课程路线、核心公式或本节目标。
- 新增热点框应是透明 shape，命名使用 `lecture-focus-generated:` 前缀，方便后续脚本重跑时清理和重建。
- 不要用关键词猜测逐句配框；优先按讲稿段落顺序和 slide 真实阅读顺序手工规划。

检查标准：

- `spotlight` 数量不必等于 `speech` 数量，但每一组连续 speech 都要有清楚的当前焦点。
- 所有 `spotlight.elementId` 必须存在于当前 scene 的 canvas elements。
- 不能有重复 action id。
- 抽查密集页，确认聚焦框不是只落在整张 slide 或过大的父区域上。
- 抽查配对文本，确认讲“第一题”时框在第一题，讲“相似三角形”时框在相似三角形，而不是只看 action 数量。

## 不同页面类型的讲法

### 概念页

先讲直觉，再讲定义。不要一开口就念定义。

好的讲法：

- “先不要看公式，先看左边图像在表达什么。”
- “这页其实是在回答一个问题：为什么我们需要这个概念？”
- “定义可以读成一句人话：……”

### 公式页

先讲公式解决什么问题，再解释每个符号从哪里来。

不要只说“公式是……”。要说明：

- 这个公式来自上一页哪一个图像或动作。
- 每个变量代表什么。
- 学生使用它时最容易漏哪一步。

### 例题页

先读题，不要直接算。

推荐顺序：

1. 题目给了什么？
2. 它在问什么？
3. 第一眼应该识别什么结构？
4. 为什么选择这个方法？
5. 每一步计算为什么成立？
6. 最后如何检查答案？
7. 这题能迁移成什么做题规则？

### 总结页

不要简单罗列本节内容。总结页要帮学生建立知识地图：

- 今天的主线是什么？
- 哪几类题对应哪种方法？
- 学生应该如何自查自己哪里不稳？
- 下一节课为什么自然出现？

## 数学课特别要求

数学讲解要慢在“判断点”上，而不是只慢在语言长度上。

例如：

- 黎曼和：慢讲宽度、采样点、高度、求和、极限分别从哪里来。
- 定积分：慢讲定积分是黎曼和极限、有向面积、端点差三种面孔。
- 换元法：慢讲为什么选 `u`，`du` 如何出现，是否换干净。
- 逆换元法：慢讲根号形状如何匹配 `sin`、`tan`、`sec`，以及为什么需要三角形回代。
- 分部积分：慢讲为什么普通换元不适合，公式如何从乘积法则来，`u` 和 `dv` 如何选择。

每道例题都要明确讲出“为什么这样选”，不能只讲“接下来令……”

## TTS 数学文本标准

讲解稿里的 `speech.text` 是给语音模型读的，不是给学生看的排版公式。slide 上可以显示标准数学符号，但讲稿必须写成语音能自然读出的中文表达。

禁止在讲解稿中直接出现：

- 幂次和下标排版：`2^n`、`x^2`、`x_i`、`x_{i-1}`、`L_4`。
- 上标、下标和特殊数学字符：`²`、`³`、`₀`、`ₙ`、`√`、`∫`、`π`、`θ`、`Δ`。
- 英文公式读法：`x squared`、`x cubed`、`pi over six`、`square root x`、`sin(2x)`。
- 紧凑微分写法：只写 `dx`、`du`、`dy` 时容易被连读，讲稿里应写成分开的语音单位。

推荐写法：

- `2^n` 写成“二的 n 次方”。
- `x^2` 写成“x 的平方”，`x^3` 写成“x 的三次方”。
- `x_i` 写成“x 下标 i”，`x_{i-1}` 写成“x 下标 i 减一”。
- `√x` 写成“根号 x”。
- `π/6` 或 `pi over six` 写成“派除以六”。
- `f(x)` 写成“f 括号 x 括号”。
- `dx`、`du`、`dy` 写成“d x”、“d u”、“d y”。
- `sin(2x)` 写成“正弦括号二 x 括号”。

检查时不能只看页面视觉效果，要扫描所有 `speech.text`。如果发现讲稿里还有 `^`、`_`、花括号、上标字符、根号、积分号、英文 squared/cubed/pi over 等残留，说明这份讲稿还没有达到语音发布标准。

## 语言风格

使用面对面口吻，像老师正在对一个具体的人讲：

- “先看左边……”
- “这里先停一下想一想……”
- “这一步不要跳过……”
- “本页真正要带走的是……”
- “下一页我们就把这个问题继续推进……”

避免：

- 在 `speech.text` 里写讲师备注，比如“要让学生明白……”“讲的时候提醒学生……”“学生应该……”。这些话可以出现在内部规划里，但不能进入讲解稿。
- 第三人称远距离表达，比如“学生会觉得……”“让学习者看到……”。要改成直接讲给正在听的人：“你现在先看……”“这里最容易错的是……”。
- 过度摘要式语言。
- 机械复述 slide 标题。
- 连续给结论但没有观察和停顿。
- 只说步骤，不解释选择理由。

## CS 课程特别要求

CS 课不要按“概念定义讲解”来写，尤其是 CPSC107。讲解主线应该是从题目到代码的设计动作：先读数据形状，再写模板，再填函数体，最后追踪执行。

### HTDF

HTDF 不能讲成清单。要讲每一步防止什么错误：

- `signature`：先限定输入和输出类型，防止 body 写偏。
- `purpose`：把题意压成一句行为承诺，防止只看函数名猜意思。
- `examples` / `check-expect`：先固定正确行为，body 写完以后才能检查。
- `stub`：先让函数有可运行的空壳，确认输出类型对。
- `template`：由数据形状给出代码骨架，不靠灵感写。
- `body`：最后才把模板里的空位填成真正逻辑。

讲 HTDF 代码页时，不要只框整块代码。至少按这些位置分别聚焦：signature、purpose、examples、stub 或 template、body、测试或调用 trace。讲稿要像 pair programming，例如“先不要写 body，先看 examples 已经承诺了什么。”

### HTDD

HTDD 的主线是：数据形状决定函数形状。

- atomic non-distinct：模板直接使用变量。
- atomic distinct / enumeration：每个固定值对应一个分支。
- interval：先检查边界和范围，再写判断。
- itemization / one-of：天然对应 `cond`，每个 case 都要问一个判定问题。
- compound data：必须用 selector 拆字段。
- reference：字段类型是另一个 HTDD，就调用对应 helper。
- self-reference：字段或 rest 回到同一个 HTDD，就出现 base case 和 recursive call。
- mutual-reference：一组数据定义互相引用，就需要一组互相调用的函数模板。

讲 HTDD 页面时，先看 data definition，再看它逼出的 template。不要把 template 当成要背的代码；要讲出“这行为什么由数据定义生成”。

### 递归与 Trace

递归课要反复追问三件事：

- base case 是哪一个输入形状？
- 哪一部分变成了更小的问题？
- recursive result 回来以后，当前层怎样组合答案？

trace 页面要按执行顺序讲，不要只说最终答案。每一段 speech 应对应当前 frame、下一次调用、返回值或组合动作。

### Code Spotlight

代码页必须尽量按行或最小代码块聚焦。理想顺序：

1. 函数头、signature 或数据定义开头。
2. purpose / interpretation。
3. examples 或 check-expect。
4. template / cond case。
5. selector、helper call 或 recursive call。
6. body 的返回表达式。
7. trace 的当前 frame 和返回结果。

如果 slide 只有一整块代码热点，允许先自动补 2-4 个透明小热点，按代码阅读顺序切成“入口、分支、递归调用、返回”。这不是最终精修，但必须比整块代码区更细，避免讲到某一行时画面还框着整片代码。
